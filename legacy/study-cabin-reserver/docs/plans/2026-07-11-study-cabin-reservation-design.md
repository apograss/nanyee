# 顺德单人学习舱自动预约系统设计

## 目标

构建一个部署在个人 VPS 上的单用户网页工具。用户可以提前创建任意未来日期的预约任务，指定固定起止时间、预约主题和学习舱优先级。系统在名额开放后自动查询并预约第一个满足完整连续时段的学习舱。

系统只预约用户明确创建的任务，不缩短时间、不拆分时段、不重复提交。

## 已确认的目标系统契约

- 站点入口：`https://infospace.smu.edu.cn/`
- API 前缀：`/ic-web`
- 登录状态：Cookie 建立会话，`GET auth/userInfo` 返回后续请求使用的 token
- 学习舱分类：`kindId=29816776`，名称为“顺德单人学习舱”
- 资源数量：18 个，分为东侧和西侧学习舱
- 查询接口：`GET /ic-web/reserve`
- 提交接口：`POST /ic-web/reserve`
- 开放时间：`08:00–22:50`
- 时间粒度：10 分钟
- 单次最短 30 分钟、最长 240 分钟
- 预约窗口参数：1440 分钟
- 当前预约验证码配置：关闭
- 预约主题：必填

这些值在运行时仍需通过公开配置和资源接口复核，避免学校调整配置后继续使用过期常量。

## 总体架构

系统采用两个应用进程和一个共享数据卷：

1. **Web 服务**：FastAPI 提供管理面板和内部 JSON API。
2. **Worker 服务**：独立进程扫描任务、管理登录态、查询资源并提交预约。
3. **SQLite 数据库**：使用 WAL 模式保存设置、任务、舱位优先级、运行状态和脱敏日志。

Web 和 Worker 由 Docker Compose 管理。应用端口只绑定 VPS 的 `127.0.0.1:8765`，外部访问通过现有 Nginx HTTPS 反向代理。

应用内部统一使用 `Asia/Shanghai`，不修改 VPS 当前的 UTC 系统时区。

## 网页面板

面板为单用户应用，包含以下页面：

- 登录：使用独立的管理员密码，不使用 SMU 密码登录面板。
- 任务列表：展示等待、预检、抢约中、成功、失败、暂停、取消状态。
- 新建/编辑任务：选择目标日期、固定开始和结束时间、预约主题、开始尝试时间、停止时间。
- 学习舱排序：拖动 18 个学习舱设置优先级，可禁用不希望使用的舱位。
- 账号状态：展示 SMU Session 是否有效、最近续期时间和脱敏账号信息。
- 尝试记录：展示查询、冲突、重试、成功和失败原因，不展示敏感凭据。
- 系统设置：轮询频率、重试上限、默认主题、默认舱位顺序等。

首版使用服务端模板和少量渐进增强脚本，避免引入完整前端构建链。

## 凭据与登录

- 管理员密码只保存强哈希。
- SMU 账号密码、Cookie 和 token 使用 AES-GCM 加密后存入数据库。
- 加密主密钥只通过容器环境变量或 Docker Secret 提供，不写入仓库和数据库。
- 日志过滤请求头、Cookie、token、密码、身份证号、手机号等敏感字段。
- Worker 优先复用有效 Session；`auth/userInfo` 失效后再触发 SSO 登录。
- SSO 登录流程针对 infospace 的实际认证地址实现，不复用教务系统固定 appid。
- 验证码识别封装为独立适配器，设置有限重试次数。连续失败时暂停自动登录并在面板告警，禁止无限请求。
- Cookie 失效、账号密码错误或系统要求额外验证时，任务保持可恢复状态，不丢失。

## 预约任务模型

每个任务至少包含：

- 目标日期
- 固定开始时间和结束时间
- 预约主题
- 有序学习舱 ID 列表
- 开始尝试时间
- 停止尝试时间
- 当前状态
- 尝试次数和最后错误
- 成功预约 ID、学习舱 ID 和确认时间

任务必须满足：目标日期未过期、时间落在开放范围、分钟符合系统粒度、时长位于允许区间、至少启用一个学习舱。同一账号、目标日期和重叠时间段默认禁止创建重复活动任务。

## 任务状态机

状态流转如下：

`WAITING → PREFLIGHT → RUNNING → SUCCEEDED`

异常分支：

- 可恢复网络错误：保持 `RUNNING`，按退避策略重试。
- Session 失效：进入 `AUTH_REFRESH`，续期后回到原状态。
- 凭据或验证码连续失败：进入 `PAUSED_AUTH`，等待用户处理。
- 超过停止时间仍未成功：进入 `FAILED_TIMEOUT`。
- 用户取消：进入 `CANCELLED`。
- 参数或规则不再合法：进入 `FAILED_VALIDATION`。

终态任务不会再次自动提交。

## 查询与提交算法

1. Worker 在开始尝试时间前完成 Session 和资源配置预检。
2. 到达开始时间后查询目标日期的全部顺德学习舱数据。
3. 根据关闭时段、已有预约、冻结间隔和开放时间计算每个舱的连续可用区间。
4. 只保留完整覆盖任务起止时间的舱位。
5. 按用户设置的学习舱优先级逐个尝试。
6. 提交前再次刷新目标舱数据，减少陈旧状态造成的冲突。
7. `POST /reserve` 成功后，调用查询接口确认预约确实存在，再将任务标记成功。
8. 若返回名额冲突，立即刷新并尝试下一优先级舱位。
9. 若全部舱位暂不可用，在任务停止时间前继续轮询。

提交使用目标系统要求的完整请求体，包括账号、目标时间、主题、成员、目标 `devId` 和必要的空字段。任务不进行时间降级或分段。

## 轮询与限流

- 等待阶段低频检查 Session 和配置。
- 临近预计放号时间提高查询频率。
- 放号窗口内采用带抖动的小间隔轮询，但限制并发为 1。
- 网络故障使用有上限的指数退避。
- 业务冲突与网络错误分别计数，避免对明确失败的请求盲目重放。
- POST 请求默认不自动无条件重试；发生响应不确定时先查询个人预约状态以判断是否已经成功。

所有默认频率采用保守值，并允许在面板中配置合理范围，避免对学校系统造成持续高负载。

## 幂等性与并发控制

- Worker 使用数据库租约锁领取任务，避免进程重启或多实例导致并发执行。
- 每个任务生成稳定的内部幂等键。
- 提交前检查本地成功记录和远端现有预约。
- 提交结果未知时先远端确认，不直接重复 POST。
- 数据库对活动任务的重复时间范围设置应用层和索引层约束。

## 错误处理与可观测性

- 每次状态变化写入结构化事件日志。
- 记录 HTTP 状态、目标系统业务 code、耗时、重试原因和脱敏响应摘要。
- `/health/live` 仅检查进程；`/health/ready` 检查数据库和 Worker 心跳。
- 面板显示 Worker 最近心跳、Session 状态和任务下一次动作时间。
- 首版以面板告警为主，通知渠道作为后续可选扩展。

## 测试策略

- 单元测试：时间范围计算、规则校验、舱位优先级、状态机、退避和幂等逻辑。
- API 客户端测试：使用录制后脱敏的响应样例，不在普通测试中访问生产站点。
- 集成测试：使用本地 fake infospace 服务模拟登录失效、放号、冲突、超时和响应丢失。
- Web 测试：验证管理员认证、任务增删改查和敏感字段不回显。
- Docker 验证：构建镜像、启动 Compose、检查健康接口和持久化重启。
- 生产前只读验证：使用真实账号查询资源和 Session，不提交预约。
- 第一次真实提交由用户明确确认后执行，并使用专门测试任务观察完整链路。

## VPS 部署约束

已只读确认目标 VPS：Ubuntu 24.04、4 核、约 8GB 内存、Docker/Compose/Nginx/1Panel 可用，系统时区为 UTC，现有 `3000–3002` 等端口已被占用。

部署时：

- 使用独立目录和命名的数据卷。
- Web 仅绑定 `127.0.0.1:8765`。
- 不复用现有容器网络或数据库。
- 不修改现有服务和端口。
- 新增域名、Nginx 配置、证书、环境变量和生产部署前再次取得用户明确确认。

## 非目标

- 多用户注册或账号共享
- 自动缩短预约时间
- 把一个任务拆成多个时段
- 同时抢多个舱位并保留多个预约
- 绕过学校的权限、封禁或人工验证
- 修改学校系统数据或规则
